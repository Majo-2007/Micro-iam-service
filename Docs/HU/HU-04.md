# Endpoints y JSON de prueba - IAM Service (HU-IAM-004)

### BASE URL

```
http://localhost:8080
```

> ⚠️ Los 3 endpoints solo exigen estar autenticado (`Bearer` válido) — todavía **no** filtran por rol/admin. Esa restricción granular es HU-IAM-006 (aún no implementada).
>
> Necesitas un `accessToken` vigente. Obtenlo primero con `POST /auth/login` (ver guía de HU-IAM-001).

---

## 1. Módulo: Catálogo RBAC

### 1.1 E1 — Listar módulos

**Endpoint**

```http
GET /modules
Authorization: Bearer {{accessToken}}
```

**Respuesta esperada**

HTTP STATUS
```
200 OK
```

Response
```json
[
  {
    "id": "b1e2c3d4-....",
    "code": "IAM",
    "name": "Identidad y Accesos",
    "description": "Gestión de usuarios, roles y sesiones",
    "displayOrder": 1,
    "iconKey": "shield"
  }
]
```

---

### 1.2 E1 — Listar roles

**Endpoint**

```http
GET /roles
Authorization: Bearer {{accessToken}}
```

**Respuesta esperada**

HTTP STATUS
```
200 OK
```

Response
```json
[
  {
    "id": "a9f8e7d6-....",
    "name": "COORDINATOR",
    "displayName": "Coordinador",
    "description": "Coordina un centro de formación",
    "systemRole": true
  }
]
```

> 📌 Copia el `id` de un rol de la respuesta — lo necesitas en el siguiente endpoint como `{{roleId}}`.

---

### 1.3 E1/E3 — Características de un rol (rol-característica con alcance)

**Endpoint**

```http
GET /roles/{{roleId}}/features
Authorization: Bearer {{accessToken}}
```

**Respuesta esperada**

HTTP STATUS
```
200 OK
```

Response
```json
[
  {
    "featureId": "c4d5e6f7-....",
    "featureCode": "USERS_MANAGE",
    "featureName": "Gestión de usuarios",
    "actionLevel": "WRITE",
    "scopeType": "GLOBAL"
  },
  {
    "featureId": "d5e6f7a8-....",
    "featureCode": "SESSIONS_VIEW",
    "featureName": "Ver sesiones",
    "actionLevel": "READ",
    "scopeType": "CENTER"
  }
]
```

> `scopeType` (`GLOBAL` / `CENTER`) es donde vive el "alcance" de la HU (criterios E2/E3 del Gherkin): cada característica otorgada por el rol indica si aplica globalmente o restringida a un centro de formación.

---

### 1.4 Caso negativo — sin token

**Endpoint**

```http
GET /modules
```
(sin header `Authorization`)

**Respuesta esperada**

HTTP STATUS
```
401 UNAUTHORIZED
```

Response
```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "Credenciales inválidas."
}
```

## 2. Prerrequisito — semillas de catálogo

Si `/modules` o `/roles` devuelven `[]` (arreglo vacío), no es un bug del backend — falta el bloqueante que la propia HU marca: *"iam-db (rbac, rbac_catalog) aplicado + semillas de módulos/características/roles"*.

Verifica en la base de datos:

```sql
SELECT code, name FROM rbac_catalog.module;
SELECT name, display_name FROM rbac.role;
SELECT role_id, feature_id, scope_type FROM rbac.role_feature LIMIT 5;
```

Si estas tablas están vacías, corre las semillas del repo `iam-db` antes de intentar demostrar la HU.

---

## 3. Resumen de escenarios

| Escenario | Endpoint | Status esperado | Qué valida |
|---|---|---|---|
| E1 · Catálogo | `GET /modules` | `200 OK` | Lista de módulos del sistema |
| E1 · Catálogo | `GET /roles` | `200 OK` | Lista de roles disponibles |
| E1/E3 · Rol-característica | `GET /roles/{id}/features` | `200 OK` | Características otorgadas por el rol, con `scopeType` |
| Negativo | Cualquiera sin `Authorization` | `401 INVALID_CREDENTIALS` | Exige autenticación |
