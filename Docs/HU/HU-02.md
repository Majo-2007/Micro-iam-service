# Guía de ejecución — HU-IAM-002
### Actualizar, cerrar sesión y gestión de sesiones

**Proyecto:** design-software-iam-service (Java / Spring Boot, hexagonal)
**Módulo:** `iam` · Capa: `backend`
**Depende de:** HU-IAM-001 (login) ya funcionando
**Objetivo:** demostrar que el refresh token renueva el access token sin rotarse (E1), que el logout revoca el refresh y reusarlo da `401 TOKEN_REVOKED` (E2), y que un usuario puede listar y revocar sesiones activas puntuales (E3) — con evidencia real en `session.refresh_token`.

---

## 0. Antes de empezar (checklist rápido)

- [ ] Docker Desktop abierto, contenedor `ds-develop-postgres-1` en estado `Up (healthy)`
- [ ] Tabla `session.refresh_token` verificada (ya la confirmaste con `\dt session.*`)
- [ ] Build compila en verde: `.\mvnw.cmd clean verify`
- [ ] Thunder Client abierto
- [ ] Terminal 1 → backend · Terminal 2 → psql de evidencias
- [ ] Usuario de prueba `maria@gmail.com` ya existe en `identity.user` (de la demo de HU-001)

> 💡 Antes de la demo en vivo, corre una vez `.\mvnw.cmd clean verify` y confirma que los 4 módulos (`iam-core`, `iam-adapters`, `contracts`, `iam-api`) salen en `BUILD SUCCESS`. Así no te arriesgas a un fallo de compilación delante del jurado.

## 3. Login inicial — obtener refreshToken (sesión A)

> Nota: la respuesta de `/auth/login` **cambió** respecto a HU-001: ahora incluye `refreshToken`.

### 3.1 Ejecutar en Thunder Client

```http
POST http://localhost:8080/auth/login
Content-Type: application/json

{
  "email": "maria@gmail.com",
  "password": "Maria@123"
}
```

**Respuesta esperada — `200 OK`:**
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "refreshToken": "8f1e2a...(valor opaco de 256 bits, no es JWT)...",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

📌 Guarda `accessToken` y `refreshToken` como variables en Thunder Client (`{{accessTokenA}}`, `{{refreshTokenA}}`). También pídele a `GET /auth/me` (con `{{accessTokenA}}`) el campo `id` — lo usas en E3 como `{{userId}}`.

### 3.2 Evidencia en base de datos

**Terminal 2:**
```powershell
docker exec -it ds-develop-postgres-1 psql -U design_software_user -d design-software-develop
```

```sql
SELECT id, user_id, device_hint, ip_address, is_revoked, expires_at, created_at
FROM session.refresh_token
ORDER BY created_at DESC
LIMIT 1;
```

✅ Esperado: una fila nueva, `is_revoked = false`, `expires_at` ~7 días en el futuro. Nota que la columna `token_hash` **no** se muestra en el `SELECT` a propósito — es el SHA-256 del token, el valor crudo nunca se persiste (así es como debe verse en la evidencia: nunca compares el token de Thunder Client contra `token_hash` directamente, son distintos por diseño).

## 4. E1 — Refresh de access token (sin rotar el refresh)

### 4.1 Ejecutar en Thunder Client

```http
POST http://localhost:8080/auth/refresh
Content-Type: application/json

{
  "refreshToken": "{{refreshTokenA}}"
}
```

**Respuesta esperada — `200 OK`:**
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...(nuevo, distinto al de login)...",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

### 4.2 Evidencia — el refresh NO se rotó

```sql
SELECT id, user_id, is_revoked, expires_at, created_at
FROM session.refresh_token
WHERE user_id = '{{userId}}'
ORDER BY created_at DESC;
```

✅ Esperado: sigue existiendo **la misma fila** de sesión A (mismo `id`, mismo `created_at`) — no se creó un registro nuevo. Eso es la prueba visual de "nuevo access_token sin rotar el refresco", tal como lo pide la HU.

## 5. Preparar E3 — segunda sesión (para multisesión)

Antes de probar logout/revoke, crea una **segunda sesión** simulando otro dispositivo, para que la demo de "múltiples sesiones activas" tenga sentido.

### 5.1 Ejecutar en Thunder Client

Repite el login, pero cambia el header `User-Agent` para simular otro dispositivo:

```http
POST http://localhost:8080/auth/login
Content-Type: application/json
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 17_0)

{
  "email": "maria@gmail.com",
  "password": "Maria@123"
}
```

**Respuesta esperada — `200 OK`:** guarda este `refreshToken` como `{{refreshTokenB}}`.

### 5.2 Evidencia — ahora hay 2 sesiones activas

```sql
SELECT id, device_hint, ip_address, is_revoked, created_at
FROM session.refresh_token
WHERE user_id = '{{userId}}'
ORDER BY created_at DESC;
```
✅ Esperado: 2 filas, ambas con `is_revoked = false`.

## 6. E3 — Listar y revocar sesiones (`GET` / `DELETE /users/{id}/sessions`)

### 6.1 Listar sesiones activas

```http
GET http://localhost:8080/users/{{userId}}/sessions
Authorization: Bearer {{accessTokenA}}
```

**Respuesta esperada — `200 OK`:**
```json
[
  {
    "id": "session-A-uuid",
    "deviceHint": null,
    "ipAddress": "127.0.0.1",
    "createdAt": "2026-08-25T...",
    "expiresAt": "2026-09-01T..."
  },
  {
    "id": "session-B-uuid",
    "deviceHint": null,
    "ipAddress": "127.0.0.1",
    "createdAt": "2026-08-25T...",
    "expiresAt": "2026-09-01T..."
  }
]
```
📌 Copia el `id` de la sesión B (la del "iPhone") como `{{sessionIdB}}`.

### 6.2 Revocar la sesión puntual (sesión B)

```http
DELETE http://localhost:8080/users/{{userId}}/sessions/{{sessionIdB}}
Authorization: Bearer {{accessTokenA}}
```

**Respuesta esperada — `204 No Content`**

### 6.3 Evidencia

```sql
SELECT id, is_revoked, revoked_at
FROM session.refresh_token
WHERE user_id = '{{userId}}'
ORDER BY created_at DESC;
```
✅ Esperado: la fila de la sesión B ahora tiene `is_revoked = true` y `revoked_at` con la hora actual. La sesión A sigue `is_revoked = false`.

### 6.4 Caso negativo — sesión inexistente → `404 SESSION_NOT_FOUND`

```http
DELETE http://localhost:8080/users/{{userId}}/sessions/00000000-0000-0000-0000-000000000000
Authorization: Bearer {{accessTokenA}}
```

**Respuesta esperada — `404 Not Found`:**
```json
{
  "code": "SESSION_NOT_FOUND",
  "message": "La sesión no existe o no pertenece al usuario."
}
```

### 6.5 Caso negativo — sin token → `401`

```http
GET http://localhost:8080/users/{{userId}}/sessions
```
(sin header `Authorization`)

**Respuesta esperada — `401 Unauthorized`:**
```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "Credenciales inválidas."
}
```
> Nota para la demo: hoy la autorización es "solo el propio usuario" (no hay roles todavía — eso es HU-IAM-006). Si el jurado pregunta si un admin puede gestionar sesiones de otros, la respuesta honesta es: **no todavía**, queda para HU-IAM-006.

## 7. E2 — Logout y reintento con token revocado

### 7.1 Cerrar sesión (revocar refresh de la sesión A)

```http
POST http://localhost:8080/auth/logout
Content-Type: application/json

{
  "refreshToken": "{{refreshTokenA}}"
}
```

**Respuesta esperada — `204 No Content`**

### 7.2 Evidencia — la sesión A quedó revocada

```sql
SELECT id, is_revoked, revoked_at
FROM session.refresh_token
WHERE user_id = '{{userId}}'
ORDER BY created_at DESC;
```
✅ Esperado: **ambas** sesiones (A y B) ahora con `is_revoked = true`.

### 7.3 Reusar el token ya revocado → `401 TOKEN_REVOKED`

```http
POST http://localhost:8080/auth/refresh
Content-Type: application/json

{
  "refreshToken": "{{refreshTokenA}}"
}
```

**Respuesta esperada — `401 Unauthorized`:**
```json
{
  "code": "TOKEN_REVOKED",
  "message": "El refresh token fue revocado."
}
```

> Este es el criterio exacto de la HU: *"revocar la actualización; reusarlo → 401 TOKEN_REVOKED"*. Nota que el sistema distingue este caso de un simple `INVALID_CREDENTIALS`: internamente el servicio chequea primero si el token está revocado (antes que expirado) para dar este código específico.

## 8. Resumen de evidencias para la sustentación

| Escenario | Endpoint | Status esperado | Qué mostrar en BD |
|---|---|---|---|
| Login (base) | `POST /auth/login` | `200 OK` | Nueva fila en `session.refresh_token`, `is_revoked=false` |
| E1 · Refresh | `POST /auth/refresh` | `200 OK` | Mismo `id`/`created_at` en `refresh_token` → no se rotó |
| E3 · Listar sesiones | `GET /users/{id}/sessions` | `200 OK` | Coincide con las filas `is_revoked=false` de `refresh_token` |
| E3 · Revocar una sesión | `DELETE /users/{id}/sessions/{sid}` | `204` | Esa fila pasa a `is_revoked=true`, `revoked_at` seteado |
| E3 · Sesión inexistente | `DELETE .../sessions/{uuid-random}` | `404 SESSION_NOT_FOUND` | — |
| E2 · Logout | `POST /auth/logout` | `204` | Fila del refresh usado pasa a `is_revoked=true` |
| E2 · Reuso tras logout | `POST /auth/refresh` (mismo token) | `401 TOKEN_REVOKED` | — |

**Consulta única para el cierre de la demo** (muestra el ciclo de vida completo de las sesiones del usuario):
```sql
SELECT id, device_hint, ip_address, is_revoked, revoked_at, created_at, expires_at
FROM session.refresh_token
WHERE user_id = '{{userId}}'
ORDER BY created_at ASC;
```
Con esto, en una sola tabla se ve: 2 sesiones creadas → 1 revocada por `DELETE /sessions/{sid}` → la otra revocada por `/auth/logout` → ambas con `is_revoked = true` y `revoked_at` distinto.

## 9. Reset completo (para repetir la demo desde cero)

```sql
DELETE FROM session.refresh_token
WHERE user_id = '{{userId}}';
```

Esto borra todas las sesiones del usuario de prueba; en el próximo login se generan filas nuevas y puedes repetir E1 → E3 → E2 cuantas veces necesites antes del día de la sustentación.

Si el jurado pregunta si esto rompió algo de la HU anterior, la respuesta es no — solo se agregó, no se modificó lógica existente:
