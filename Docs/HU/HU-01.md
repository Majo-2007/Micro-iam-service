# Guía de ejecución — HU-IAM-001
### Inicio de sesión, bloqueo por intentos y auditoría

**Proyecto:** design-software-iam-service (Java / Spring Boot, hexagonal)
**Módulo:** `iam` · Capa: `backend`
**Objetivo:** demostrar en vivo que el login funciona (E1), rechaza credenciales inválidas (E2), bloquea la cuenta tras 5 intentos fallidos (E3) y expone la identidad autenticada (E4) — con evidencia real en base de datos para cada caso.

---

## 0. Antes de empezar (checklist rápido)

- [ ] Docker Desktop abierto y el contenedor `ds-develop-postgres-1` en estado `Up (healthy)`
- [ ] Thunder Client (o Postman) instalado en VS Code
- [ ] Terminal 1 reservada para correr el backend (Spring Boot)
- [ ] Terminal 2 reservada para las consultas SQL de evidencia
- [ ] Usuario de prueba `maria@gmail.com` ya insertado en `identity.user` (paso 2)

> 💡 Tip para la sustentación: ten las dos terminales y Thunder Client visibles en pantalla al mismo tiempo (divide la pantalla en 3), así muestras request → respuesta → evidencia en BD sin cambiar de ventana cada vez.

---

## 3. E1 — Login exitoso

### 3.1 Ejecutar en Thunder Client

```http
POST http://localhost:8080/auth/login
Content-Type: application/json

{
  "email": "maria@gmail.com",
  "password": "Maria@123"
}
```

**Respuesta esperada — `200 OK`:**
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "tokenType": "Bearer",
  "expiresIn": 900
}
```

📌 **Copia el `accessToken`** — lo necesitas para el paso E4. En Thunder Client puedes guardarlo en una variable de entorno (`{{accessToken}}`) para no copiarlo a mano cada vez.

### 3.2 Evidencia en base de datos

En **Terminal 2** (psql):

```sql
SELECT email, is_active, failed_attempts, locked_until, last_login_at
FROM identity."user"
WHERE email = 'maria@gmail.com';
```
✅ Esperado: `failed_attempts = 0`, `locked_until = NULL`, `last_login_at` con la hora actual.

```sql
SELECT email_attempted, outcome, ip_address, attempted_at
FROM identity_audit.audit_login
WHERE email_attempted = 'maria@gmail.com'
ORDER BY attempted_at DESC
LIMIT 1;
```
✅ Esperado: una fila nueva con `outcome = SUCCESS`.

## 4. E2 — Credenciales inválidas

### 4.1 Ejecutar en Thunder Client

```http
POST http://localhost:8080/auth/login
Content-Type: application/json

{
  "email": "maria@gmail.com",
  "password": "ClaveIncorrecta"
}
```

**Respuesta esperada — `401 Unauthorized`:**
```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "Credenciales inválidas."
}
```

### 4.2 Evidencia en base de datos

```sql
SELECT email, failed_attempts, locked_until
FROM identity."user"
WHERE email = 'maria@gmail.com';
```
✅ Esperado: `failed_attempts` subió en 1 (por ejemplo, de 0 a 1).

```sql
SELECT email_attempted, outcome, attempted_at
FROM identity_audit.audit_login
WHERE email_attempted = 'maria@gmail.com'
ORDER BY attempted_at DESC
LIMIT 1;
```
✅ Esperado: `outcome = INVALID_PASSWORD`.

---

## 5. E3 — Bloqueo de cuenta (RN-IAM-01)

### 5.1 Repetir el request de E2 hasta 5 veces

Vuelve a enviar el mismo `POST /auth/login` con password incorrecta **4 veces más** (para totalizar 5 fallos seguidos). Cada vez, la respuesta sigue siendo `401 INVALID_CREDENTIALS`.

**Evidencia intermedia** (opcional, muéstrala mientras subes el contador):
```sql
SELECT failed_attempts FROM identity."user" WHERE email = 'maria@gmail.com';
```

### 5.2 En el intento número 5 o siguiente

```http
POST http://localhost:8080/auth/login
Content-Type: application/json

{
  "email": "maria@gmail.com",
  "password": "Maria@123"
}
```

Aunque uses la password **correcta**, la cuenta ya está bloqueada.

**Respuesta esperada — `423 Locked`:**
```json
{
  "code": "ACCOUNT_LOCKED",
  "message": "Cuenta bloqueada hasta 2026-08-24T20:15:00Z."
}
```

### 5.3 Evidencia en base de datos

```sql
SELECT email, failed_attempts, locked_until
FROM identity."user"
WHERE email = 'maria@gmail.com';
```
✅ Esperado: `failed_attempts >= 5`, `locked_until` con una fecha ~15 minutos en el futuro (RN-IAM-01: 5 fallos → 15 min; 10 fallos → 24 h).

```sql
SELECT email_attempted, outcome, attempted_at
FROM identity_audit.audit_login
WHERE email_attempted = 'maria@gmail.com'
ORDER BY attempted_at DESC
LIMIT 1;
```
✅ Esperado: `outcome = ACCOUNT_LOCKED`.

### 5.4 (Opcional) Desbloquear para continuar la demo

Si necesitas seguir probando sin esperar los 15 minutos:
```sql
UPDATE identity."user"
SET failed_attempts = 0, locked_until = NULL
WHERE email = 'maria@gmail.com';
```

## 6. E4 — Obtener identidad autenticada (`/auth/me`)

> Requiere un `accessToken` válido. Si tu cuenta quedó bloqueada en el paso anterior, desbloquéala (5.4) y vuelve a hacer login (paso 3) para obtener un token fresco.

### 6.1 Con token válido

```http
GET http://localhost:8080/auth/me
Authorization: Bearer {{accessToken}}
```

**Respuesta esperada — `200 OK`:**
```json
{
  "id": "b6e2a1f0-....",
  "email": "maria@gmail.com",
  "firstName": "Maria",
  "lastName": "Oyola",
  "actorType": "USER"
}
```

### 6.2 Sin token (para mostrar el caso negativo)

```http
GET http://localhost:8080/auth/me
```
(sin header `Authorization`)

**Respuesta esperada — `401 Unauthorized`:**
```json
{
  "code": "INVALID_CREDENTIALS",
  "message": "Credenciales inválidas."
}
```

### 6.3 Evidencia

Este endpoint es de solo lectura, no modifica base de datos. La evidencia aquí es la respuesta misma del `200 OK` con los datos del usuario — muéstrala junto al `SELECT` del paso 3.2 para probar que el `id`, `email`, `firstName` y `lastName` coinciden exactamente con la fila de `identity."user"`.

## 7. Resumen de evidencias para la sustentación

| Escenario | Endpoint | Status esperado | Qué mostrar en BD |
|---|---|---|---|
| E1 · Login OK | `POST /auth/login` | `200 OK` | `identity.user.failed_attempts=0`, `identity_audit.audit_login.outcome=SUCCESS` |
| E2 · Credenciales inválidas | `POST /auth/login` | `401 INVALID_CREDENTIALS` | `failed_attempts` incrementado, `outcome=INVALID_PASSWORD` |
| E3 · Bloqueo (5 fallos) | `POST /auth/login` | `423 ACCOUNT_LOCKED` | `locked_until` con fecha futura, `outcome=ACCOUNT_LOCKED` |
| E4 · Identidad autenticada | `GET /auth/me` | `200 OK` (con token) / `401` (sin token) | Datos devueltos coinciden con la fila de `identity.user` |

**Consulta única para mostrar todo el historial de auditoría al final:**
```sql
SELECT email_attempted, outcome, ip_address, user_agent, attempted_at
FROM identity_audit.audit_login
WHERE email_attempted = 'maria@gmail.com'
ORDER BY attempted_at ASC;
```
Esta consulta, corrida al final de la demo, muestra en una sola tabla toda la secuencia: `SUCCESS → INVALID_PASSWORD (x4) → ACCOUNT_LOCKED → SUCCESS`, que es la mejor evidencia visual de que la HU-01 quedó completa.

## 8. Reset completo (para repetir la demo desde cero)

```sql
UPDATE identity."user"
SET failed_attempts = 0, locked_until = NULL, last_login_at = NULL
WHERE email = 'maria@gmail.com';

DELETE FROM identity_audit.audit_login
WHERE email_attempted = 'maria@gmail.com';
```

Con esto el usuario queda como recién creado y puedes repetir la secuencia E1 → E2 → E3 → E4 cuantas veces necesites antes del día de la sustentación.
